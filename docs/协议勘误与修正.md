## 1. 严重问题（会导致实现走错路，必须修正）

### 1.1 审批方法名选用了 legacy 代际

**原文**（落地方案 5.4、appserver 调研 3.3）：
> 审批 | 服务端主动请求 → `applyPatchApproval` `execCommandApproval`

**实测**：这两个方法名在 0.155.1 中确实存在，但源码明确标注为 **DEPRECATED**：

> `/// DEPRECATED APIs below`
> `/// Request to approve a patch. This request is used for Turns started via the legacy APIs (i.e. SendUserTurn, SendUserMessage).`

现行主路径是三个 v2 方法：

| 方法 | 用途 |
|---|---|
| `item/commandExecution/requestApproval` | 命令执行审批 |
| `item/fileChange/requestApproval` | 文件变更审批 |
| `item/permissions/requestApproval` | 权限提升申请 |

`ServerRequest` 全集共 10 个，审批占其中 3 个（另有 `item/tool/requestUserInput` 用于向用户提问、`mcpServer/elicitation/request` 用于 MCP 交互）。

**影响**：按原文实现会一路走到 legacy 路径，拿不到 v2 Item 语义，且上游随时可能移除。
**修正**：以 `item/*/requestApproval` 为唯一实现目标；legacy 方法仅作兼容读取，不主动使用。

### 1.2 `approval/resolve` 方法不存在

**原文**（appserver 调研 3.3）：
```json
["approval/resolve", "$reqId", { "approvalId": "apr_xxx", "decision": "allow_once", "scope": "thread" }]
```

**实测**：在 252 个协议方法名中，`approval/resolve` **零命中**。

服务端发起的审批就是一个普通的 JSON-RPC 请求（带 `id`），客户端**直接回应那个 `id`** 即可：

```jsonc
// server → client
{ "method": "item/commandExecution/requestApproval", "id": 0, "params": { /* ... */ } }

// client → server（就是普通 JSON-RPC 响应，没有额外包装）
{ "id": 0, "result": { "decision": "accept" } }
```

契约测试实测：审批请求顶层 `id=0`，回应后轮次正常收尾。

**附带机制**：服务端会广播 `serverRequest/resolved` 通知（含 `requestId` 与 `threadId`），用于告知「这个请求已被解决」——多客户端或超时竞争时靠它收敛状态，原文未提及。

### 1.3 握手报文形态与响应字段均不符

**原文**（落地方案 5.2、appserver 调研 3.1）：
```json
["initialize", 0, { "clientInfo": {...} }]
=> { "id": 0, "result": { "serverInfo": {...}, "capabilities": { "threads": true, "approvals": true } } }
["initialized", null, {}]
```

**实测**：

| 项 | 原文 | 实际 |
|---|---|---|
| 报文形态 | 数组 `["method", id, params]` | 对象 `{"method":..., "id":..., "params":{...}}` |
| `initialize` 响应 | `serverInfo` + `capabilities` | `userAgent` / `codexHome` / `platformFamily` / `platformOs` |
| `initialized` 通知 | `["initialized", null, {}]` | `{"method":"initialized"}`（**无 params 字段**） |
| 能力协商位置 | 响应里的 `capabilities` | **请求侧** `capabilities.experimentalApi` |

实测响应：
```json
{ "id": 1, "result": {
  "userAgent": "kcode-contract/0.155.1 (Mac OS 26.5.0; arm64) dumb (kcode-contract; 0.1.0)",
  "codexHome": "/private/var/.../kcode-home-HR5duM",
  "platformFamily": "unix",
  "platformOs": "macos"
}}
```

**修正**：
- 解析器接受对象形态；不要假设存在 `serverInfo`。
- 实验能力通过 `initialize` **请求**的 `capabilities.experimentalApi` 主动申请，且需在 `InitializeCapabilities` 中声明 `optOutNotificationMethods` 可抑制不需要的通知。
- `codexHome` 可用于校验 app-server 是否在使用预期的状态目录——这是隔离验证的关键抓手。

### 1.4 决策值集合与「编辑命令」不存在

**原文**（落地方案 3.4）：
> Allow once ｜ Allow for this profile ｜ Always require ｜ Deny ｜ **Edit command**

**实测** `CommandExecutionApprovalDecision` 共 6 个变体：

| 决策 | 语义 |
|---|---|
| `"accept"` | 批准本次 |
| `"acceptForSession"` | 批准，且本会话内同类请求不再询问 |
| `{"acceptWithExecpolicyAmendment": {"execpolicy_amendment": [...]}}` | 批准，并落盘一条 execpolicy 规则使后续匹配命令免询问 |
| `{"applyNetworkPolicyAmendment": {...}}` | 为该 host 落盘持久网络策略规则 |
| `"decline"` | 拒绝，Turn 继续 |
| `"cancel"` | 拒绝，**并立即中断该 Turn** |

`FileChangeApprovalDecision` 为 4 值：`accept` / `acceptForSession` / `decline` / `cancel`。

**修正**：
- 「Edit command」**不是协议决策值**——它是纯客户端功能：改写命令后重新发起，属自研工作量，需明确标注。
- `decline` 与 `cancel` 语义不同（后者会中断 Turn），UI 必须区分，原文把两者混为「Deny」。
- 「Always require」不是决策值，是策略层（`granular`）配置。
- `acceptWithExecpolicyAmendment` / `applyNetworkPolicyAmendment` 是官方给出的「避免审批疲劳」正解——原文完全未提。

## 2. 中等影响（功能设计需要据此调整）

### 2.1 协议中不存在 risk tier 字段

**原文**（落地方案 3.4、7 章 `ApprovalModal`）把「影响多大 / risk tier」列为审批必答项，并给出四级 `RiskTier`。

**实测**：协议无任何 `risk` 字段。审批参数提供的是**原始事实**——命令字符串、cwd、命令解析结果 `commandActions`、网络上下文 `networkApprovalContext`、可写根申请 `grantRoot`、以及模型给出的 `reason`。

**修正**：
- 风险分级是**纯客户端推断层**，必须在方案中标为自研模块（建议命名 `RiskClassifier`），不可暗示可读协议字段。
- 唯一的「官方风险信号」是 `approvalsReviewer: "auto_review"`——由官方子代理预审并给出结论，见 2.2。自研分级应与之互补而非重复。
- 推断层须遵守原则：**推断结果只影响展示与排序，不得作为放行依据**（原文 6.3 已有此原则，但未点明它同时适用于自研分级器）。

### 2.2 `approvalsReviewer` 与自动审查完全缺失

**实测**：`ApprovalsReviewer` 枚举为 `user` / `auto_review` / `guardian_subagent`。

> `auto_review` uses a carefully prompted subagent to gather relevant context and apply a risk-based decision framework before approving or denying the request. The legacy value `guardian_subagent` is accepted for compatibility.

配套通知：`item/autoApprovalReview/started`、`item/autoApprovalReview/completed`、`autoApprovalReview/strictReviewRequired`。

另有 `ApprovalsReviewer.strict_auto_review` 字段（在 permissions 审批响应中）用于「本 Turn 后续命令全部先预审」。

**修正**：这是官方对「审批疲劳」的正面回答，应作为 Phase 2 的核心项写入方案；原文只在范式调研中一笔带过，落地方案完全没有。

### 2.3 沙箱参数在两个方法上形态不同（易踩坑）

**实测**：

| 方法 | 字段 | 形态 |
|---|---|---|
| `thread/start` | `sandbox` | 字符串枚举 `SandboxMode`：`"read-only"` / `"workspace-write"` / `"danger-full-access"` |
| `turn/start` | `sandboxPolicy` | **对象** `SandboxPolicy`（tagged union） |

`turn/start` 的对象形态实测回显：
```json
{ "type": "workspaceWrite", "writableRoots": [], "networkAccess": false,
  "excludeTmpdirEnvVar": false, "excludeSlashTmp": false }
```

可选 `type`：`dangerFullAccess` / `readOnly` / `externalSandbox` / `workspaceWrite`，且 `readOnly` 与 `workspaceWrite` 各带独立 `networkAccess`。

**修正**：适配层要接受两种形态并统一为领域模型，否则「创建线程」与「提交轮次」两处策略会不一致。

### 2.4 `turn/interrupt` 不是幂等的

**原文**（落地方案 5.5 第 7 项、验收清单）：
> 实现 `turn/interrupt`，同一轮次幂等
> `turn/interrupt` 幂等，重复调用不产生副作用

**实测**：
- 参数为 `{threadId, turnId}` **两者必填**（0.155.1 实测缺失即报错）。
- 对不存在的 turn 调用返回 **JSON-RPC 错误 `-32600 "no active turn to interrupt"`**，而不是幂等成功。

**修正**：把「幂等」改为**「语义收敛」**：客户端需将 `-32600` 与「Turn 已结束」视为同一终态，并依赖 `turn/completed` 事件而非 RPC 返回值判定结束。原文 5.5 结尾的「关键边界」（状态只能来自事件）本已正确，此处应引用它而非另立「幂等」要求。

### 2.5 版本基线严重滞后

**原文**：强制 `≥ 0.39.0`。
**实测**：npm `latest` 为 **0.155.1**（另有 `0.156.0-alpha.9`）。

`0.39.0` 是 CVE 的**修复版本**，作为安全下限正确，但作为**开发基线**已落后约 116 个发布，会错过 v2 审批、granular 策略、auto_review 等全部现代能力。

**修正**：区分两个概念——**安全下限** `0.39.0`（不可低于）与**开发基线** `0.155.1`（本仓库锁定版本，见 `codex.lock.json`）。

### 2.6 审批档位归类错误 + `granular` 缺失

**原文**（落地方案 6.3）把 `danger-full-access` 列入审批策略档位表。

**实测**：`danger-full-access` 是 **sandbox mode**（`SandboxMode` 枚举），不是 approval policy。原文自己的 5.1 节分类正确，6.3 节与之矛盾。

`AskForApproval` 实测为：
```
"untrusted" | "on-request" | "never" | { "granular": {
    sandbox_approval: bool, rules: bool, skill_approval: bool,
    request_permissions: bool, mcp_elicitations: bool } }
```

- `on-failure` **不是枚举值**，只是 `OnRequest` 的 serde alias（历史兼容）。
- `granular` 是 5 个分类开关的组合，用于「该弹的弹、不该弹的放」——正是原文 3.4 想解决的问题的官方答案，落地方案却未收录。

### 3.10 补充发现：`declined` 是被遗漏的 Item 状态（Rust 阶段实测）

原文与本文档早先版本都未记录这一点。在把契约测试移植为 Rust 实现后，用「工作区内 + 工作区外」双标记探针实测了审批决策的真实语义：

| 决策 | 提权是否生效 | 命令是否执行 | `item.status` | `exitCode` |
|---|---|---|---|---|
| `accept` | ✅ | ✅ 提权执行 | `completed` | `0` |
| `decline` | ❌ | **❌ 完全不执行** | **`declined`** | `null` |
| `cancel` | ❌ | ❌ 不执行 | **`declined`** | `null` |
| 非法值（如 `allow_once`） | ❌ | ❌ 不执行 | — | — |

`CommandExecutionStatus` 与 `PatchApplyStatus` 的实际枚举为：

```
["inProgress", "completed", "failed", "declined"]
```

**三条被实测确认、值得持续守护的安全属性**（已固化为 `crates/codex-bridge/tests/approval_semantics.rs`）：

1. **`decline` 是硬拒绝，不会降级执行。** 关键证据是工作区**内**的标记文件同样未创建——若只看区外文件，「拒绝提权但仍在沙箱内跑一遍」的实现也会通过。这个区别直接决定 UI 文案：若 `decline` 会降级执行，按钮写「拒绝」就是误导。
2. **非法决策值 fail-safe。** 发送协议中不存在的决策值不会被当作批准（实测 0.155.1 行为正确）。这条必须守住——否则客户端任何拼写错误都会静默放行本应拦截的高危操作。**v1.0 文档中的 `allow_once` 正是一个不存在的值**，若上游行为某天变成 fail-open，后果严重。
3. **UI 必须渲染 `declined` 状态。** 否则用户拒绝后看到的是一张「已完成」的命令卡片，无法分辨命令究竟跑没跑。

> **方法说明**：这三条都是先写出探针、看到反直觉结果（`decline` 下 `item/completed` 依然到达）、再用更精确的探针推翻初步结论才得到的。若只验证「命令是否执行」而不区分沙箱内外，会得出「decline 没有阻止执行」的错误结论——本文档早先的探针就一度得出该错误判断，已修正。

### 3.11 踩坑记录：带 tag 的 serde 枚举不会重命名变体内部字段

这不是协议问题，是**实现层容易犯且难以察觉的错误**，值得单独记录。

在领域层定义 `ItemBody` 时写成：

```rust
#[serde(rename_all = "camelCase", tag = "kind")]
pub enum ItemBody {
    CommandExecution {
        exit_code: Option<i64>,        // ← 会原样序列化成 "exit_code"
        aggregated_output: Option<String>,
    },
    // ...
}
```

**规则**：容器级的 `rename_all` 只作用于**变体名**（`CommandExecution` → `commandExecution`），
**不会**作用到变体内部的字段。多词字段必须逐个变体标注 `#[serde(rename_all = "camelCase")]`。

**为什么难发现**：`status`、`command`、`cwd` 这类单词字段两种写法恰好一致，
掩盖了问题。只有 `exit_code` / `aggregated_output` / `duration_ms` 会漏。
前端按 `exitCode` 读取时永远拿到 `undefined`，而**后端单测只要不校验线格式就全绿**——
本次就是这样：集成测试通过、领域单测通过，但序列化出去的是 `exit_code`。

**发现方式**：集成测试断言 `exitCode == 0` 失败。原始报文里该字段明明是 `0`，
说明问题在投影/序列化而非协议——顺着这条线索定位到 serde 属性作用域。

**固化**：`crates/kcode-domain/src/model.rs` 的
`item_body_serializes_with_camel_case_field_names` 显式校验线格式，
并已用变异测试确认它能捕获该回归（移除 `rename_all` 后立即失败）。

**推广**：任何要交给前端的类型都必须有**线格式断言**，不能只测 Rust 侧的值相等。
语言间的字段命名差异不会产生编译错误，只会产生 `undefined`。

### 3.12 文件变更与 diff 的两个通道（Rust 领域层实测）

实现审阅面板时必须先搞清 diff 从哪来。实测发现协议提供**两个通道**，
可用性与格式都不同——这一点 schema 完全看不出来。

#### 通道一：`fileChange` Item 的 `changes[]`（条件可用）

`schema` 只声明 `diff: string`，**没有任何说明**。实测其内容随 `kind` 变化：

| `kind` | `diff` 字段的**实际内容** |
|---|---|
| `add` | **完整文件内容**，不是 diff |
| `delete` | **完整被删内容**，不是 diff |
| `update` | hunk 文本，**不含** `---`/`+++` 文件头 |
| `update` + `movePath` | hunk 文本 + 尾部 `\n\nMoved to: <绝对路径>` |

三条由此推出的实现要求：

1. **不能用同一个解析器处理所有情况。** 对 `add`/`delete` 套用 diff 解析器
   会得到「+0 -0」——因为找不到 `@@` 头。这在审阅面板上表现为「文件变更了但
   显示零行改动」。
2. **重命名的重复信息要剥掉。** 目标路径同时出现在 `kind.movePath` 与 diff
   尾部，尾部那份参与解析会产生噪声警告。
3. **路径是绝对路径。** 直接显示会占满整行并暴露目录结构，需相对化到工作区。

#### 通道二：`turn/diff/updated` 通知（稳定可用）

载荷是**标准 unified diff**（含 `diff --git`、`new file mode`、文件头、`@@` 头）：

```
diff --git a/hello.txt b/hello.txt
new file mode 100644
index 0000000..3b18e51
--- /dev/null
+++ b/hello.txt
@@ -0,0 +1 @@
+hello world
```

#### 可用性差异（决定架构选择）

| 通道 | 触发条件 |
|---|---|
| `turn/diff/updated` | **稳定**：只要工作区发生变更就推送（含沙箱内直接应用的情形） |
| `fileChange` Item | **条件性**：并非所有文件变更都产生该 Item。实测同一 `apply_patch` 命令在沙箱内直接放行时**不产生** `fileChange` Item，但文件确实被写入且 `turn/diff/updated` 有推送 |

**架构结论**：审阅面板以 `turn/diff/updated` 为**主数据源**（稳定、格式标准），
`fileChange` 的逐文件结构作为**补充**（有则更精细，无则不影响可用性）。
把主次搞反会导致面板在常见路径下空白。

**测试影响**：`decline` 文件变更的语义测试因此改写。原测试假设 `apply_patch`
必经审批，实测失败——它在该路径下不经过审批。拒绝语义的实际验证由**命令路径**
承担（那条路径确实走审批，且已验证 `decline` 是硬拒绝）。

> **一条推广**：`schema` 说明字段**可能存在**，不说明**实际会填什么**，更不说明
> **何时会出现**。本次三个问题（内容形态、重复信息、触发条件）都只能实测得知。

### 3.13 测试夹具的不确定性会同时制造假阴性与假阳性

并发隔离测试最初用「按顺序发放的脚本」驱动 mock：线程 1 拿脚本第 0 项、
线程 2 拿第 1 项。这在并发下**不成立**——谁先发出请求谁拿到第 0 项。
于是出现了两种可能：测试可能无端失败，也可能在真串线时因恰好错位而通过。

改为**回显 mock**（把用户消息原样作为回复返回）后，内容与线程严格对应，
判定不再依赖时序。并用变异测试确认：让 `replay_items` 忽略线程过滤后，
该测试立即报出「A 线程出现了另一线程的内容」。

**教训**：涉及并发的测试夹具必须是**确定性**的。用共享计数器分配预期值、
依赖请求到达顺序、依赖 wall-clock 时序，都属于同一类隐患——
它们不会让测试报错，只会让测试的结果失去意义。

### 3.14 第四次遇到 serde 的 camelCase 陷阱

`FileChangeKind::Update` 的 `move_path` 字段又一次漏了 `rename_all`。
这次是**线格式契约测试**（`wire_contract.rs`）抓到的——该测试对
所有跨语言类型的每个键做 snake_case 扫描，因此不需要人去记住这个坑。

前三次分别出现在 `ItemBody` 变体、`AppEvent` 变体、嵌套结构体。
**结论**：这类问题靠「记得写属性」防不住，只能靠自动化扫描。

### 3.15 GUI 手工验收发现的三个问题（自动化测试全都测不到）

Phase 1 首次实际运行桌面应用（`npm run tauri build` 产物）时发现三个缺陷。
它们的共同点是：**穿过全部 172 项 Rust 测试与 44 项前端测试**，因为那些测试
直接调用 Rust/TS API，从不经过 IPC 层与真实 WebView。

#### 问题一：Tauri 2 capability 缺失导致 IPC 静默失效（最严重）

**现象**：应用启动正常、状态点变绿、`codex app-server` 子进程在跑、
事件日志里有 3 条 `thread_started` 记录——但侧栏始终显示「尚无线程」。

**根因**：Tauri 2 **默认不授予任何权限**。没有 capability 声明时：

- 构建**完全成功**，没有任何编译错误或警告
- `invoke` 与 `listen` 在运行时被**静默拒绝**（不抛异常、不打印日志）
- 后端把事做成了，前端一无所知

修复：新增 `crates/kcode-desktop/capabilities/default.json`，声明
`core:default` 与 `core:event:default`（事件监听是前端接收领域事件的唯一通道）。

**为什么测试测不到**：Rust 集成测试直接调 `AgentService`，不经过 Tauri IPC；
前端测试用 jsdom，`inTauri()` 返回 false 从而整条 IPC 路径被跳过。
两侧的测试都是绿的，缺口在中间的粘合层。

新增 `scripts/verify-tauri-capabilities.sh` 并在 CI 中执行——
它检查 capability 文件存在、含必需权限、`windows` 字段非空。

#### 问题二：错误信息显示为 `[object Object]`

**现象**：启动失败时错误区显示 `[object Object]`，用户完全不知道发生了什么。

**根因**：`String(e)` 对 Tauri 的错误载荷无效。Tauri 的 `invoke` 在命令返回
`Err` 时抛出的是反序列化后的对象（`{ message: string }`），字符串化得到
`[object Object]`，真实原因丢失。前端 7 处都这么写。

修复：新增 `extractErrorMessage()` 处理各种形态（字符串、`Error`、
`{message}`、`{error}`、嵌套、循环引用兜底），替换全部 7 处。

同时给 `KcodePaths::resolve` 加了工作区存在性校验——此前传入不存在的目录
会静默失败，现在给出明确提示与用法说明。

#### 问题三：`send_turn` 缺少事件广播（保留，但理由更正）

**排查过程**：发现 `start_thread` / `send_turn` 的成功路径只写事件日志、
不广播 `AppEvent`，于是补上了广播，并在注释中断言「app-server 不会为此
另发通知」。

**变异测试推翻了该断言**：移除主动广播后，新增的测试**仍然通过**。
实测确认 app-server **确实会**推送 `thread/started` 通知：

```
thread/start 之后收到的通知: remoteControl/status/changed, thread/started
```

因此：注释写错了，新测试也无法区分事件来源（它验证的是「事件最终可达」，
这本身有价值，但不等于「广播存在」）。广播**保留**，理由更正为
**消除时序依赖**（命令响应与通知的到达顺序不保证）。

**这一段的价值**：如果没做变异测试，这段错误的注释会长期留在代码里，
误导后续维护者。

> **方法论**：GUI 验收不可被自动化测试替代。上述三个问题分别属于
> IPC 粘合层、错误传播路径、以及运行时事件通道——都是「各层单测都绿、
> 整机却不工作」的典型位置。

### 3.16 验收报告的自我修正：「后端有能力」≠「用户能看到」

**被质疑的点**（用户原话：「现在好像离 zcode 或者 codex 差距很远」）。

- 前端启动时 `refreshThreads()` 填充侧栏；点击线程触发 `openThread()`

- 新增两个测试走**公开 API**：`threads_survive_restart_via_public_api`、

**推广到验收方法论**：任何「可恢复 / 可审计 / 可导出」类主张，都必须在

本报告此后对所有此类主张都标注「验证方式」是走用户路径还是走内部 API。

### 3.17 性能问题：三个根因都不是 React

用户报告「启动先白屏」与「双击最大化有空白」。逐项实测后，三个根因
**都在 React 之外**——把它当成框架性能问题会查错方向。

#### 根因一：视口单位在 WebView 中更新滞后

**现象**：双击标题栏最大化后，内容只画到旧宽度，右侧与底部空白。

**证据**：用户截图是全屏 4480×2280，但内容右边界只在 x≈2891
（逻辑宽度 ≈1445）——恰好是**初始窗口宽度 1440**。窗口已最大化，
但布局仍按旧尺寸算。

**根因**：`html, body, #root { height: 100% }` 是相对父级的高度链路，
而 `.app` 用了 `height: 100vh`。**视口单位在 Tauri/WKWebView 中更新
滞后于窗口实际尺寸**——resize 后 `100vh` 仍是旧值，于是内容不铺满。

**修复**：改用纯百分比链路（`html → body → #root → .app` 全为 100%），
弹窗的 `100vw`/`86vh` 同理替换。实测确认：最大化后无空白。

> **注**：用 AppleScript `set size` 测试**复现不出来**——那条路径的
> resize 事件与用户双击标题栏不同。必须用真实交互（合成双击）才能重现。

#### 根因二：窗口背景色配置项不存在

`tauri.conf.json` 里**没有** `backgroundColor` 字段（我最初写进去，
被静默忽略了，白屏依旧）。Tauri 2 必须用运行时的
`set_background_color()`。

**同时改了窗口显示时机**：窗口初始 `visible: false`，等前端完成
首次挂载后调用 `frontend_ready` 再显示，并加 3 秒超时兜底
（防止前端异常时用户对着空进程发呆）。

实测：从启动第一帧起窗口即深色（RGB 41,44,50），无白色闪烁。

#### 根因三：合成开销（这才是真的性能问题）

- **5 处 `backdrop-filter`（30-44px 模糊）+ 3 个持续动画的光斑**：
  动画元素上的大半径模糊会强制每帧重新合成。光斑改用**预模糊的径向
  渐变**（视觉等价，零运行时开销），模糊半径下调到 18-24px。
- **缺 `contain: paint`**：backdrop-filter 元素的任何变化都可能触发
  上层重绘，加 `contain` 把范围限制在元素内。

另加两条降级：`@supports` 检测不支持模糊时退回不透明背景；
`prefers-reduced-motion` 时停掉持续动画。

#### 顺带修的观感问题

最大化后中栏过宽、文字行被拉到 2000px 以上。三栏都设了宽度上限
（`minmax` 生长到上限为止），Markdown 段落加 `78ch` 行宽限制。

**推广**：桌面应用的「性能问题」需要分层归因——框架、宿主、渲染合成
是三个独立层。直接归因到框架会漏掉后两层，而本例中后两层才是主因。

### 3.18 最大化空白的第二个来源：媒体查询断点导致的「慢半拍」

前一节（3.17）修掉了 `100vh` 滞后。但用户复测后反馈：
**双击缩放时仍有空白，且布局切换慢半拍**。

#### 排查：先排除 React

```
grep -rn "addEventListener('resize'|ResizeObserver" src/
→ 零命中
```

**React 完全不参与 resize 布局**——它没有任何 resize 监听，布局由 CSS Grid
独立完成。所以不是「React 响应式布局慢」。用户提到 Codex/ZCode 用 Electron
很顺滑，这个方向本身就指错了：问题不在框架选型。

#### 三个真实机制

**机制一：媒体查询断点依赖滞后的视口宽度**

CSS 里有两个宽度断点（1180px / 980px）。断点依据的是**视口宽度**，而
视口在 WKWebView 中更新滞后于窗口尺寸——窗口已变宽，媒体查询仍按旧值
判定，随后突然切换。这正是「慢半拍」的观感来源。

已移除断点：Grid 的 `minmax` 本身会在容器内平滑伸缩，不需要断点。
（原 980px 断点还是死代码：窗口 `minWidth` 已是 1024px。）

**机制二：模糊层数过多**

同时存在 5-6 个 `backdrop-filter` 表面（sidebar、main、右侧每个面板各一）。
resize 时每层都要重新光栅化。

处理：
- **右侧面板改实色半透明**（不再是 backdrop-filter）。层数从 5-6 降到 2。
  深色背景下视觉差异极小——对比截图确认观感一致。
- 模糊从 30-44px 降到 18-24px。

**机制三：模糊层与滚动容器重叠**

`backdrop-filter` 原先直接放在 `.sidebar` / `.main` 上，而这两个元素内部
有滚动区域——滚动或内容变化时都要重新模糊。

改为「**模糊背景层 + 内容层**」结构：`::before` 绝对定位承载模糊，
内容层 `z-index: 1` 浮在其上。模糊层不随内容滚动。

#### 我引入的一个反优化

上一轮（3.17）我加了 `contain: paint` 想限制重绘范围。**这是错的**：
对 `backdrop-filter` 元素加 `contain` 会多出一层，且缩窄浏览器可优化的
采样范围。已全部移除。

#### resize 期间降级

即使做完上述优化，双击标题栏时窗口动画由 macOS 的 WindowServer 驱动，
而内容重绘要等应用进程跟上——动画期间每帧重算模糊，内容必然滞后。

新增：resize 开始即关闭模糊（改用不透明底色），停止 150ms 后恢复。
用**原生监听**而非 React 状态——resize 每秒可触发数十次，走 React 会把
渲染开销加到本就吃紧的合成路径上，与优化目的相反。

#### 测量结论与局限

连拍测量（小区域截图约 160ms/帧）：50 帧中仅 **1 帧**出现空白，
之后内容全程稳定。

**但这个精度测不出「慢半拍」的确切时长**——160ms 的采样间隔
无法分辨 100ms 与 300ms 的差异。此处如实标注：优化方向有明确机制支撑
（减少模糊层数、消除视口依赖、resize 期间关闭模糊），
但**缺少毫秒级的前后对比数据**。要精确验证需用录屏逐帧分析
（如 `ffmpeg` 抽帧），本次未做。

### 3.19 白色标题栏：既不是 Tauri 的锅，也不是窗口适配问题

用户截图显示窗口顶部有一条白色横带、右侧一块白区，并推测
「Tauri 不如 Electron 顺滑」。

#### 测量推翻两个猜测

**猜测一：绘制区与窗口尺寸不匹配（上一节修的那个）**
写脚本 `verify-window-fit.sh` 测量后：绘制区 1839×1018 vs 窗口 1840×1019，
**只差 1px 边框**。该问题已不存在。

**猜测二：macOS 自动标签页**
tao 源码（`platform_impl/macos/window.rs:321`）**已主动调用**
`setAllowsAutomaticWindowTabbing(false)`；Tauri 配置文档也说明
「`tabbingIdentifier` 不设置时自动标签页自动禁用」。
标签栏是多实例场景的产物，不是默认行为。

#### 真正的根因：标题栏背景是系统默认色

放大截图后看清：那条白带就是**窗口标题栏本身**——macOS 上 Tauri 窗口
默认使用系统标题栏，浅色系统下即白色，与深色内容形成刺眼对比。

**修复**：改用 `titleBarStyle: "Overlay"` + `hiddenTitle: true`，
内容延伸到标题栏之下，红绿灯直接浮在深色背景上。
再把 `trafficLightPosition` 调到 `{x:16, y:18}` 避开侧栏内容。

#### Overlay 的代价：窗口不再可拖拽

这是文档明确写的前提（`TitleBarStyle::Overlay` 注释）：
> You need to define a custom drag region to make your window draggable,
> however due to a limitation you can't drag the window when it's not in focus.

必须显式加 `data-tauri-drag-region` 区域。实测验证：
- 窗口**未聚焦**时拖拽无效（上游限制 tauri#4316，非缺陷）
- 先点击聚焦再拖拽 → 窗口正常移动（(400,150) → (560,269)）

#### 新增验证脚本

`scripts/verify-window-fit.sh`：用 CoreGraphics 枚举窗口（而非 AppleScript——
后者在自动标签页场景下取不到正确的窗口），截图后扫描非白像素范围，
比较绘制区与窗口尺寸。容忍 4px 误差（边框与抗锯齿）。

实测有效：默认尺寸、放大后均通过；`visible:false` 变异会正确报出
「进程存活但没有任何可见窗口」。

### 3.20 「DOM 正确但画不出来」：WebKit 的合成层问题

对齐 Codex 界面时遇到一个最难排查的现象：**右栏内容完全不可见，
但所有可测指标都正常**。

#### 排查过程（三轮假设，前两轮都错了）

**假设一：grid 少了一列。** 检查 `.app` 的直接子元素：5 个（拖拽条、
光斑、sidebar、main、inspector），其中两个是 `position: fixed` 不占位，
正好 3 列。**排除。**

**假设二：`pointer-events` 拦截。** 用浏览器 `elementFromPoint` 在右栏
中心取样，命中的是 `.ambient` 里的光斑 `<span>`。给 `.ambient` 加
`pointer-events: none` 后命中测试恢复正常——**但视觉上依然空白**。
说明这不是命中问题。

**假设三（正确）：WebKit 未给该元素分配合成层。**
在 Tauri 应用内注入诊断，把计算值回报到日志：

```json
{"appZ":"1","ambPos":"fixed","ambPE":"none","inspW":460,
 "inspVisible":"visible","inspOpacity":"1","hitClass":"inspector",
 "inspChildren":4,"firstPanelW":460}
```

**宽度 460、可见、不透明、有 4 个子元素、命中正确——CSS 与 DOM 全对，
但 WebKit 就是不绘制它。** 这与 Chromium 行为不同（浏览器里一直正常）。

**修复**：给 `.inspector` 显式背景 + `transform: translateZ(0)` 强制
独立合成层。修复后右栏立即显示。

#### 为什么会这样

右侧面板自身背景是透明的，靠子面板的实色背景呈现。当它与相邻的
`backdrop-filter` 元素（`.sidebar::before` / `.main::before`）共存时，
WebKit 的层分配可能让这个透明容器得不到独立层，从而被跳过绘制。

上一轮为了减少合成开销，我把模糊从 5-6 层降到 2 层并移到 `::before`——
这个优化本身是对的，但**留下了这个副作用**。

#### 方法论上的教训

**「DOM 正确」不等于「渲染正确」。** 这次三轮假设里，前两轮都是用
浏览器工具（Chromium）测的，全部正常；问题只在 WebKit 里存在。
跨引擎的渲染问题必须**在目标引擎里验证**，用截图像素比对，
而不是用 DOM 查询或计算样式推断。

### 3.21 装了系统代理的机器上，本地 provider 一律不通（实测）

**现象**：在一台开了系统代理的 macOS 上跑 `npm test`，第一道闸门（协议契约）就挂：

```
✗ 收到服务端审批请求 — 25000ms 内未收到；已见通知: …, error
✗ 模型流量全部打到本地 mock provider — mock 收到 0 次 Responses 请求
```

14 项断言里 12 项通过，失败的两项都与「模型流量」有关。**看起来像协议实现出错。**

**查证过程**：

| 步骤 | 结论 |
|---|---|
| 打印 app-server 的通知载荷 | 拿到真因：`unexpected status 502 Bad Gateway: Unknown error, url: http://127.0.0.1:<mock端口>/v1/responses` |
| 502 是谁发的？ | **不是 mock**——它只回 200 / 404，且 `/stats` 计数为 0，说明请求根本没到它 |
| 中间是谁？ | `scutil --proxy`：系统开着 HTTP/HTTPS/SOCKS 代理（`127.0.0.1:7897`，Clash 类工具） |
| 例外列表生效吗？ | **不生效**。列表里明确写了 `127.0.0.1` 与 `localhost`，codex 的 HTTP 客户端仍把回环请求交给了代理 |
| 反证 | 只加 `NO_PROXY=127.0.0.1,localhost`，其余不变：**22/22 通过**，mock 收到 2 次请求 |

**判定**：这是 codex HTTP 客户端的行为（继承系统代理，但不读系统代理的例外列表），
不是 KCode 引入的。但它有三个实际后果，都不能不管：

1. **仓库自带的契约测试在有系统代理的机器上必然失败**，而 CI（无系统代理）永远看不到。
   这类「只在开发者机器上出现」的失败，恰好是「本地可复现」主张的反面。
2. **产品侧同样成立**：用户用本地 provider——Ollama / LM Studio / 本地 relay——
   会拿到 502，而那个端口一次请求都收不到。本项目自己的验收文档里就记录过
   用户环境存在 `127.0.0.1:15721` 的本地 relay，正是会踩中的配置。
3. **`verify-no-egress.sh` 的观察会被污染**：它把「回环 → 回环」的连接当正常过滤掉，
   而代理连接恰好长这样——等于把「模型流量被代理吞掉」误判成「没有出站」。

**修法**：把回环地址并入**子进程**的 `NO_PROXY`，且**合并而非覆盖**（否则会把用户
原有的代理例外抹掉）：应用侧 `SpawnConfig::child_env()`、脚本侧 `scripts/no-proxy-env.mjs`、
shell 侧 `export NO_PROXY="127.0.0.1,localhost,::1${NO_PROXY:+,$NO_PROXY}"`。
大小写两份都设——不同 HTTP 客户端读的键不同。

**教训**：判断这类故障只需问一句「**对端真的收到请求了吗**」。
mock 的计数为 0 就说明流量压根没送到，问题不在协议层、不在模型层，
而在更下面的传输路径上——先看对端计数，能省掉一整轮对着协议字段的空排查。

### 3.22 更正：「OpenAI CDN 段」是误判，那是被污染的 DNS 应答

修好 §3.21 的代理问题后，出站抓取脚本第一次看见了 codex 的**真实外连目标**——
在此之前所有流量都被代理吞掉，抓取结果里只剩「回环 → 回环」的连接，
被脚本当作正常过滤，于是这份安全验收长期是**盲的**。

**现象**：`verify-no-egress.sh` 报非预期连接（`… -> 66.220.146.94:443 (SYN_SENT)`），
而白名单只认早期文档认定的 `2a03:2880::/32`。

**查证**：

| 步骤 | 结果 |
|---|---|
| 反查早期文档所依据地址的 PTR | `2a03:2880:f117:83:face:b00c:0:25de` → **edge-star-mini6-shv-01-tpe1.facebook.com** |
| 本机对 `api.openai.com` 的多次查询 | 199.59.150.49（PTR `r-199-59-150-49.twttr.com`）、208.77.47.172、108.160.162.104、173.208.182.68……**每次查询都在变** |
| 本机对 `api.chatgpt.com` 的查询 | 31.13.73.169 → PTR `edge-z-p4-shv-01-dub4.facebook.com` |
| 公共解析器对照 | 经本机网络查 `1.1.1.1` 得到的应答同样是伪造地址（UDP/53 出口一并被拦） |
| 实测连接目标 | 108.160.166.62 恰等于当时本机对 `chatgpt.com` 的应答；157.240.8.41 的 PTR 为 `cmon-checkout-edge-shv-01-syd2.facebook.com` |
| 对照：`cdn.openai.com` | 指向 `openaiassets.azureedge.net`（Azure Front Door）——OpenAI 的 CDN 在 Azure 侧，不在 Meta 侧 |

**判定**：本机 DNS 对这两个域名的应答是**伪造的**（落在 Facebook / Twitter 段、每次查询都不同、
无可用 PTR —— DNS 注入的典型特征）。因此：

1. 「codex 在 `thread/start` 期间发起一次未配置的元数据拉取，连接未建立、无数据传输」——
   这个**事实成立**，披露它是对的；
2. 但「该目标 = OpenAI 官方 CDN 段（Meta 托管）」这个**归属是错的**。把污染应答当成上游服务地址，
   正是「拿观测到的地址反推归属」最容易踩的坑。**在 DNS 不可信的网络里，任何基于地址的归属都不可靠。**

**处置**：

1. `verify-no-egress.sh` 不再按固定网段白名单，改为**逐条归属**：PTR 落在 `facebook.com` / `twttr.com`、
   或目标**等于本机此刻对该端点的 DNS 应答**、或落在 `2a03:2880:` 兜底段——三者任一成立才算
   「上游元数据拉取」，并打印归属依据；三条都不成立即失败。
2. 无法归属时**不默认放行**：需显式 `KCODE_ALLOW_UNATTRIBUTED_METADATA=1`，且输出中留痕。
3. `SECURITY.md` 与 Phase 1 验收报告同步更正归属表述。

**教训**：「观测到的地址属于谁」必须由可验证的归属（PTR / DNS 应答 / 注册信息）支撑，
不能由「它出现在这一段」推断。这也再次说明 §3.21 那类传输层问题会**连带污染安全结论**——
代理把目标藏起来时，验收脚本的「通过」并不代表没有出站，只代表它看不见。

### 3.23 更正：出站脚本的两处判定语义缺陷（复盘自查发现）

§3.22 修好归属逻辑后，复查脚本输出时发现两处**与脚本自己宣称的原则相悖**的问题。
两者都不是「漏放行」（没有让计划外出站溜过去），而是**报告不可信**——
对一个主张「你能验证我在做什么」的项目来说，这类偏差同样必须记账。

**现象 A（计数偏小）**：脚本注释写着「逐条归属并单独计数，而非静默忽略」，
但 `2a03:2880:` 兜底前缀仍在归属循环**之前**被并入 `ALLOWED_PATTERN` 提前放行。
命中它的连接既不打印归属依据，也不计入任何一类。

| 轮次 | 采集到的连接 | 报告的「上游元数据拉取」 |
|---|---|---|
| 1 | 2 条（含 1 条 `2a03:2880:`） | **1 条** |
| 2 | 1 条（`2a03:2880:`） | **0 条** |

报告数字系统性偏小，而且小的正是「最没有归属证据的那一类」——正是最该被看见的那类。

**现象 B（缺正向对照，「0 条」具误导性）**：报告里的 `本地 mock provider : 0 条`
来自 lsof 轮询，而回环连接的存活时间常短于 0.4s 采样间隔，抓不到是常态。
读者看到「0 条」会以为模型链路没走通，但注入 mock `/stats` 诊断后确认
**实际收到 2 次请求**。反过来更危险：若哪天 `NO_PROXY` 修复回归、请求又被代理吞掉，
同一行「0 条」**看起来一模一样**——观察者分不出「链路通但抓不到」与「链路真没通」。
这两种情况必须能区分，否则脚本又会回到 §3.21 的盲通过。

**修法**：

1. 兜底前缀移出白名单，纳入逐条归属循环，作为第三条依据打印并**计入** `META_HITS`。
2. 新增正向对照：mock provider 的 `/stats` 实收请求数（不受轮询粒度影响）。
   **为 0 或读不到即失败**——那次抓取到的连接无法代表真实行为，不能据此判定出站情况。
   报告同时给出 lsof 条数，并注明「轮询采样，可为 0」，两者要一起读。

修后实测（2 轮）：正向对照 2 次请求、上游元数据 2 条逐条打印归属依据
（一条 PTR 归属、一条等于本机 DNS 应答），采集条数与报告条数一致。

**教训**：验收脚本的**判定语义**本身就是被审计的对象。「白名单提前放行」会让
放行的那部分脱离归属流程——哪怕它确实属于预期类别，也应该带着依据一起计数。
另外，凡是以「观测到某计数」为证据的脚本，都必须回答一个反向问题：
**这个计数为 0 时，是「真的没发生」还是「我没能看见」**。回答不了，
就需要一个不受观测方式影响的正向对照。

### 3.24 `thread/revert` 不还原本地文件——落地方案的假设不成立

落地方案（`docs/KCode落地方案.md` 第 269、273 行）把「撤销变更」列为逐文件能力，
并注明「撤销变更可使用 `thread/revert`」。**这个假设是错的**：锁定版本（0.155.1）
的 schema 自己写明了它不干这件事。

```
ThreadRevertParams.beforeTurnId:
  "Turn excluded from the replacement history, together with every later turn."
  "This only changes persisted conversation history. It does not revert local file changes."
```

已废弃的 `thread/rollback` 说得更直白：

```
  "...does not revert local file changes that have been made by the agent.
   Clients are responsible for reverting these changes."
```

即：这两个方法动的是**会话历史**（替换某一轮之后的记录），
**工作区里的文件不在它们的职责范围内**，由客户端自己负责。

**处置**：逐文件撤销改由客户端实现（`kcode-bridge/src/git.rs::revert_file`），
按文件在 git 中的真实状态分派动作——已暂存先撤出暂存区、已跟踪恢复自索引、
未跟踪则删除。这与 Git 面板的其它能力同源（协议不提供 git 能力，故自研）。

**为什么这条必须记账**：若照着方案直接调 `thread/revert`，用户点「撤销这个文件的
改动」会得到**成功响应**，而文件一个字节都没变——属于最难排查的一类缺陷
（接口成功、状态未变）。同族的教训还有 §3.16「后端有能力 ≠ 用户能看到」，
这里是「协议有方法 ≠ 它做的是你要的事」。凡要用一个方法前，先读它的**参数与
返回的文档注释**，别从方法名推断语义（`revert` 这个名字的直觉正是「还原代码」）。

### 3.25 CI 从来没有运行过：一处 `if:` 表达式让整个 workflow 失效

**发现过程**：本次提交后按惯例核对 CI，发现新 run 结论为 failure。继续查时
注意到两件事同时对不上——该 run 的**显示名是文件路径**而不是 `name:` 字段的值，
且**它一个 job 都没有**（`GET /actions/runs/<id>/jobs` 返回 `total_count: 0`）。
再拉全部历史 run：**18 次推送、18 次 failure，从项目第一次提交起无一例外**。

从 run 页面拿到了真正的错误：

```
Invalid workflow file: .github/workflows/protocol-contract.yml#L1
(Line: 98, Col: 13): Unrecognized named-value: 'secrets'
Located at position 1 within expression: secrets.KCODE_MODEL_API_KEY != ''
```

`secrets` 上下文**不允许出现在 `if:` 表达式里**（可用在 `env` / `with` / `run`）。
而这一处表达式让**整个文件**判定为无效。后果是：

- job `verify`（协议漂移、协议事实清单、codex 版本与哈希）
- job `rust`（单元测试、集成测试、clippy、测试数字漂移、出站验证、capability）
- job `web`（前端单测、类型检查、构建）

**一条都没有执行过**。而 README 在此期间一直写着「协议行为由 CI 持续验证」，
「当前状态」表里六项标着 ✅。这些勾是本地手工跑出来的真实结果，但**没有任何
外部机制在持续复核**——「持续验证」这句话当时是不成立的。

**修复**：把判断挪到 job 级 `env`（`HAS_MODEL_KEY: ${{ secrets... != '' }}`），
步骤上写 `if: env.HAS_MODEL_KEY == 'true'`，密钥值仍只挂在那个步骤上
（不给整个 job 的每个步骤都塞一遍）。同时修掉同一文件里第二个错误：
集成测试写的是 `cargo test -p codex-bridge`，而 crate 名是 **`kcode-bridge`**
（第一个 job 根本没跑到那一步，所以这个错误此前从未暴露）。

**新增防线**：`scripts/verify-workflow.sh`，接入 `npm test` 与 CI 的 `verify` job。
它把本次踩到的两类错误钉成规则（`if:` 里出现 secrets、`cargo -p` 用了非成员包名），
并校验 run 引用的脚本都存在。两条规则都用「注入真实 bug」验证过会报错，
而不是写完就算。

**这个检查的盲区（写在脚本头部，也必须写在这里）**：它兜不住「本文件自身失效」
——文件无效时整个 workflow 不跑，检查自己也就不会被执行。它的价值在本地
`npm test` 与「坏在别的 job / 别的文件」这两处。兜住自身失效只能靠**外部观测**：
确认某次推送**真的产生了 job**，而不是一个 0 job 的 run。

**教训（与 §3.23 同源，但这次咬的是自己）**：

1. **「配置正确」和「配置生效」是两件事。** 前几节反复在说脚本的判定语义要被
   审计，这次轮到 CI 自己——一个从未运行过的流水线，其绿灯与否不含任何信息。
   判断依据不能是「文件里写了什么步骤」，而必须是「这些步骤真的跑过」。
2. **静默失效的形态是「看起来没发生」，不是「看起来失败了」。** 0 job 的红 run
   在网页上只是一闪而过的红叉；`name` 显示为文件路径是唯一的线索。凡是「应该有
   东西发生」的位置（job、测试、告警），都要能回答「它上次真的发生了吗」。
3. **README 里的 ✅ 需要有外部机制背书。** 本地跑通是真的，但把「我跑过」写成
   「持续验证」是过度承诺。本轮之后，这句话才第一次名副其实。

### 3.26 CI 首次真跑暴露的两个「只在干净环境失败」的缺陷

修好 §3.25 之后，CI 第一次真正执行，三个 job 全部起来了（run 名从文件路径
变回 `protocol-contract`，job 数从 0 变 3——这是修复生效的直接证据）。
随即暴露出两个**长期被掩盖**的缺陷：

**缺陷 A：codex 哈希把「平台特定产物」当成全局唯一。**
`codex.lock.json` 里只有一个顶层 `sha256`，那是**本机 macOS arm64 二进制**的。
而 npm 为每个平台装不同二进制（darwin-arm64 / linux-x64 / …），哈希必然不同——
同一份 lock 在开发机上通过、在 CI 的 Linux 上永远失败。

修法：改为按平台记录（`platforms[<os>-<arch>]`），每个平台各自比对；
当前平台**未记录**时明确提示而非静默通过，并保留对旧格式的兼容
（读到顶层 sha256 时给出迁移建议）。三个分支都实测过：未记录（提示，不失败）、
不匹配（失败并打出两个哈希）、旧格式（通过 + 迁移提示）。

**缺陷 B：测试隐式依赖开发机上的既有配置。**
`git::tests::commit_all_creates_commit` 走的夹具只用**环境变量**提供提交身份，
而产品代码 `commit_all` 启的是干净子进程、不继承它们。开发机有全局
`user.name` 所以一直通过；ubuntu runner 没有，于是必失败。

修法：夹具把身份写进**仓库配置**（测试环境即真实环境），并顺带改进产品代码——
`commit_all` 现在会先查身份，缺失时给出可照做的指引（哪两项配置、具体命令），
而不是把 git 的 `Please tell me who you are.` 原样透给用户。

**关键工具：`scripts/test-in-clean-env.sh`。**
两次都是「本地全绿、CI 必红」，根因是**本地能复现出 CI 的失败是新能力，不是运气**。
这个脚本把开发机与 runner 的差异显式化：无全局/系统 git 配置、干净的 HOME、
无 `KCODE_*` 覆盖。它当场就复现出了缺陷 B——**在 CI 报告之前**。

**这个脚本自己也被咬了三下**（都记在脚本注释里，因为它们正是同一类错误的缩影）：

1. 它先改掉 `HOME` 再去找 `cargo`，于是永远找不到（工具链属于「安装」，
   不该被「用户配置」的清理波及）；
2. 清掉 `RUSTUP_HOME`/`CARGO_HOME` 后 rustup 直接报
   `could not choose a version of cargo to run`（同上，属于工具安装）；
3. 把 `GIT_AUTHOR_NAME` 等设为**空串**（而不是删掉）——git 会区别对待
   「设置为空」与「未设置」，空值**压过**仓库配置并报
   `fatal: empty ident name`。而 runner 上这些变量是不存在的，不是空的。
   于是它制造出了「CI 上不会发生」的失败。

第 3 条最值得记：**模拟环境本身必须与目标环境同构**，否则会引入方向相反的
假信号——既可能掩盖真问题，也可能把你引向修一个不存在的 bug。
判断依据是「这个差异在目标环境里到底是什么状态」，而不是「清得越干净越好」。

**共性**：这两个缺陷都属于「开发机上永远绿」的那一类。它们能被发现，
不是因为某个测试写得更严，而是因为**第一次真的在目标环境里跑了**。
这与 §3.25 是同一件事的两面：没有真实执行，一切绿灯都不含信息。

（协议漂移、协议事实清单、codex 哈希、契约测试、前端单测、类型检查、构建），

| `long_output_is_delivered_intact` | 767 | 长输出命令状态应为 `Completed` |

**这三个测试与本次改动无关**（`acceptance.rs` 最后一次修改是 `8811322`，
早于本次会话；本次未触碰该文件）。它们是**项目从未在 Linux 上跑过**的直接
后果——此前 18 次推送 CI 一次都没执行（§3.25），所以这些平台差异从未暴露。

**为什么这里只记录、不修复**：三个用例都依赖真实执行
（`apply_patch`、shell heredoc、命令输出聚合），而 Linux 上 codex 的
行为路径与 macOS 不同。在没有 Linux 环境可反复验证的条件下盲改，很可能
把它们改成「本地通过、CI 仍失败」，甚至为迎合测试而弱化断言——那比留着
红灯更糟。**红灯是诚实的状态**，按项目的记账原则，如实写进本节。

**给接手者的线索**：
- 三个 panic 的完整输出可在 CI 的 job 页面读到（日志下载需 admin 权限，
  但注解与失败摘要在页面上可读；`scripts/ci-summarize-failures.sh` 会把
  失败用例名与断言详情输出到注解面板）。
- 最可能的差异方向（按可能性排序，均未验证）：**命令的 shell**（ubuntu 上
  `/bin/sh` 是 dash，`<<'PATCH'` 的 heredoc 行为与 macOS 的 bash 不同）、
  `apply_patch` 在 Linux 上的落盘路径、`ls`/`cat` 等命令的输出格式差异。
  验证方式：在 ubuntu 容器里跑单个用例，而不是在 macOS 上猜。
- **注意不要把断言改弱来换绿灯**——这三条断言的内容（diff 行数、重启后
  历史一致、长输出完整）正是「可恢复」与「可审计」两个主张的核心。

**后续（同日晚）：把诊断能力补进断言本身。**

在无 Linux 环境、无 admin 日志权限的条件下，「再跑一次看看」拿不到更多线索——
因为 CI 注解面板只显示**短行**，而一句 `未找到命令 Item` 无法区分三种根因
完全不同的情况：命令根本没执行 / 执行了但类型不符 / Item 存在却没重放出来。

所以改用**自诊断断言**：三个用例在失败时把现场拼进 panic 消息
（Item 类型序列、轮次状态、命令退出码与输出字节数、本地重跑命令）。
本地注入真实失败验证过输出：

```
未找到命令 Item。
实际 items：userMessage, agentMessage
轮次状态：Completed（若为 failed，说明命令侧出错而非重放问题）
本地重跑：cargo test -p kcode-app --test acceptance history_survives_restart -- --nocapture
```

**这条经验值得单独记**：当失败环境不可直接访问时，**让代码自己报告现场**
比反复尝试访问环境有效得多。它与 §3.23「报告的判定语义本身要被审计」是
同一条原则的延伸——判据不只是「测试失败了」，而是「失败信息是否足以定位」。
一个只说出「某处失败」的断言，在受限环境里等于没有诊断。

**诊断结果（同日晚，CI 注解面板）**：自诊断立了功，一次就拿到关键现场：

```
实际 items：userMessage, agentMessage
轮次状态：Completed（若为 failed，说明命令侧出错而非重放问题）
```

即：**模型发出了命令调用、轮次正常收尾，但命令 Item 根本没产生**。
失败清单里还多了 `apply_patch_without_escalation_applies_directly`，
说明 `apply_patch` 同样没有落地。

**这个现场排除了哪些假设**（这就是自诊断的价值）：

| 假设 | 判定 |
|---|---|
| shell 语法差异（`<<'PATCH'` 在 dash 下行为不同） | **排除**——`echo hello`、`seq 1 12000` 这类极简命令同样不产生 Item |
| 命令本身失败（退出码非 0） | **排除**——那会留下 `cmd[...]` 项并带 exit code，而 items 里连 cmd 项都没有 |
| 重放/持久化丢数据 | **排除**——`轮次状态：Completed` 说明不是重放问题，是执行结果从未产生 |

**剩下的方向**：命令执行通道在 Linux 上没起来。最可能是 **workspace-write
沙箱在 ubuntu runner 上不可用**——macOS 用 seatbelt，Linux 依赖 landlock
或 bubblewrap，而 runner 的内核/权限未必满足（`unprivileged_userns_clone`
在较新的 Ubuntu 上常被禁用）。沙箱不可用时 codex 会拒绝执行命令，而**我们的
客户端目前没有把这个信号呈现出来**——这本身是一个可改进点：如果沙箱起不来，
用户看到的应该是「命令没跑」的明确原因，而不是时间线上什么都不发生。

**已加的自检**：workflow 里新增「沙箱前提自检」步骤（仅失败时执行），
打印内核版本、`unprivileged_userns_clone`、`max_user_namespaces`、
landlock LSM 是否启用、`bwrap` 是否存在、seccomp 状态——让上述假设
可被**证实或排除**，而不是继续猜。这是本机能做的最后一步；真正的修复需要
在 Linux 上验证（本机无容器运行时，见 §3.27 开头的说明）。

**仍未做**：修复本身。方向已收窄到「沙箱前提」，但具体修法是「换沙箱后端」
还是「测试改用 `--dangerously-bypass-approvals-and-sandbox` 之外的路径」
（注意：验收测试**不应该**为了跑通而绕过沙箱——那会削弱被验证的安全属性），
需要在 Linux 环境里试。宁可留着红灯并附上完整证据链，也不在没有验证条件的
情况下改测试断言。

## 4. 安全章节的事实核查

原文附录 B 列了 ZCode 事件的 12 条具体断言，**未给出任何引用**，且这些断言是第 6 章安全设计与第 12 章对比表的立论前提。经独立核查：

### 4.1 核查结论：整体「部分可支持」

绝大多数断言能在公开来源中找到对应，但存在**两个实质性问题**：

**问题一：全部精确数字源自同一样本，不构成独立验证。**
`62 次`、`564 次`、`42,411 文件`、`86.6%`、`29.6%`、`56.8%` 六个数字全部出现在公开来源中，但**全部源自同一份原始取样**（一份 313MB 的 macOS 商业工作区）。其余转载（issue、聚合仓库、媒体报道）属同源复述，**表面上的多来源不等于独立验证**。独立样本给出的 `.git` 占比差异很大（另一取证报告为 62–90%；第三份为 26 个工作区平均 82.9%、最高 96.7%）。

**问题二：有两条与来源存在实质矛盾。**

| 原文断言 | 核查结果 |
|---|---|
| 「上传失败会**无限重试**（观测到 564 次）」 | **与来源矛盾**。564 确为原文数值，但第三方复盘指出 `failureCount` 是**跨任务累计计数**，而非上传失败次数；真实重试记录在 `attemptCount`，**上限 3 次、最长保留 24 小时**。原始取证报告也只是记录该值从 564 涨到 565，**未断言「无限重试」** |
| 「**唯一**有效缓解：文件系统层锁目录…」 | **与来源冲突**。该表述源自原始取证报告的主张，但另有至少两类不同思路的缓解方案：asar 补丁禁用采集、网络层屏蔽 |

另需注意：厂商声明的「已修复」**未出现在厂商官网**，最初发布于用户群与社交平台，经媒体转载——应标注为**二手转述**而非一手公告。后续第三方在致歉后版本上的反向验证显示：上传管线代码**仍保留在客户端**，变更主要是开关默认值翻转与服务端配置下线。

### 4.2 处置决定

**决定：重写为「可验证的架构承诺」，不再依赖该事件的细节数字。**

理由有三：

1. **不必依赖。** 本方案真正的卖点是「开源客户端 + 零静默上传 + 可导出审计 + 本地优先」，这些靠自身架构即可立住，不需要借竞品事故证明。
2. **风险不对称。** 引用未经一手验证的具体数字，一旦被指出偏差，反而会削弱「可审计」这一核心主张的可信度——对一个以「你能验证我在做什么」为卖点的产品，这是最不该有的弱点。
3. **方法一致。** 本方案对协议细节坚持「先跑 `generate-json-schema` 校验」，安全叙事理应适用同一标准：**只写能给出来源、或能由本仓库脚本验证的断言**。

**改写原则**：
- 保留**架构级约束**（禁止宿主级采集 sidecar、禁止静默外发、开关必须真实生效）——这些是本项目自身的设计承诺，不需要外部事件背书。
- 删去所有具体数字与未经一手确认的机制细节；如需保留案例，只保留「曾有工具因默认开启的代码库索引功能发生工作区数据外发，厂商已致歉并承诺开源与第三方审计」这一层，并标注为**媒体报道的二手转述**。
- 第 12 章对比表中「静默全量上传（已致歉）」改为不依赖细节的表述。

### 4.3 相应地，隐私红线第 4 条的表述需要收紧

原文第 4 条：「禁止『开关形同虚设』。每个隐私开关必须有**单一、可验证的语义**…开关关闭后必须能在网络层观测到行为停止。」

这条本身正确，且**是目前最有价值的红线**——核查显示「开关未拦截采集链」正是事件的核心争议点。建议补强为可执行形式：

- 每个隐私开关必须在 `SECURITY.md` 中写明「关闭后具体不发生什么」。
- 每条开关须有一条**自动化验证**：关闭后由抓包/文件系统监控确认对应行为停止（对应验收清单，见 `SECURITY.md`）。
- **开关的关闭路径必须有代码级测试**，而不只测 UI 状态——「开关只存在于 schema 而无拦截分支」是可复现的失败模式。

## 6. 对原文的保留评价

以下原判断经核对**正确且有价值**，应在后续工作中保持：

- **「请求响应只确认方法已被接受，不代表轮次完成」**——实测证实：`turn/start` 立即返回 `turn.id`，后续状态只能从事件流获得。
- **stdio 唯一生产路径**，不开本地监听端口。
- **适配层隔离官方 wire type**——本次勘误本身就是这条结论的实证：协议在 116 个发布内变化极大。
- **冻结 schema + CI 差异比对 + 保留 raw_json**。
- **`generate-json-schema` 必须在实现前先跑**——本次核对正是执行了这一步才发现全部问题。
- **默认 `on-request`、最小可写根、禁止 `--dangerously-bypass-approvals-and-sandbox` 作常规配置**。
- 隐私红线的**架构级约束**（而非设置项）定位。
